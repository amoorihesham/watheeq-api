**Scope of this doc:** Technology and architecture decisions. Product and scope decisions live in `MVP_SCOPE.md` (D1-D46).

**Guiding rule:** for the MVP, choose the simplest design that is correct for the current requirements.
Hardening that the MVP does not need yet is listed under "Deferred hardening" and added when the product grows.

---

### Constraints

- **Language / framework:** Node.js + TypeScript, Express.
- **Data residency:** all tenant data must remain in Saudi Arabia.
  This includes databases, backups, logs, and any third-party service that receives tenant data (for example error tracking or an email provider).
- **Primary client:** a browser web app. A mobile app is a distant future client.

### Decision Log

| #   | Decision | Rationale | Alternatives considered |
| --- | -------- | --------- | ----------------------- |
| T1  | **PostgreSQL** as the database | Relational data (org tree, roles, requests), strong transactions, managed offerings available in KSA | MySQL, MongoDB (poor fit for relational data and cross-document transactions) |
| T2  | **Tenant isolation: shared tables with a `tenant_id` column, filtered in application code.** Every repository function that reads or writes tenant data takes the tenant ID and filters by it. One database role is used for everything. | Simplest model to build, run, and debug; no database roles or policies to provision on the KSA host. The data layout is the same one RLS needs, so RLS can be added later without moving data. | PostgreSQL Row-Level Security (stronger: the database refuses cross-tenant rows even if a query forgets the filter; deferred), schema or database per tenant |
| T3  | **Drizzle ORM** for data access; **migrations generated by Drizzle Kit** from `src/db/schema/` | Typed queries and explicit transactions; one source of truth for tables, no hand-written SQL migrations | Kysely, Prisma |
| T4  | **One `users` table for every account**, with a `role` column: `operator` (platform operator, belongs to no tenant) or `user` (tenant user) | One login flow, one table, one set of auth code | Separate `operators` table and login realm (stronger separation; deferred) |
| T5  | **Tenant membership through a `tenant_members` table** with a unique `user_id`, so a user belongs to exactly one tenant, and a `role` for the user inside the tenant (`admin` or `member` until Phase 3 replaces it with tenant-defined roles). `tenants.owner_id` points to the tenant's owner. | Keeps `users` free of tenant columns (operators have none), while the unique constraint keeps the MVP's one-user-one-tenant rule a database fact | `users.tenant_id` column; many-to-many membership (not needed by the MVP) |
| T6  | **Email is unique across the platform**; login finds the user, and through membership the tenant, from the email | Matches one-user-one-tenant; no tenant code or subdomain at login | Subdomain per tenant, tenant code at login |
| T7  | **Authentication with tokens in httpOnly cookies:** a signed JWT access token (30 minutes; payload `{sub, iss: "watheeq_api", iat, exp, username, email, role, tenant}`) and an opaque refresh token (7 days) stored hashed in the database, rotated on every refresh, revoked on logout; refresh rejects inactive users | No database read on ordinary requests; a deactivated user loses access within 30 minutes; one mechanism for operators and tenant users | Server-side sessions in PostgreSQL (immediate revocation, but a database read per request), external IdP (extra infrastructure, residency concerns) |
| T8  | **Audit entries are written in the same transaction** as the business change, through `writeAuditEntry(tx, entry)`, which accepts only a transaction | Audit can never disagree with the actual data | Log files, asynchronous audit writes |
| T9  | **Modular monolith** organized by feature modules | One deployable; clear module boundaries without network and operational overhead | Microservices |
| T10 | **Express 5, zod, pino, Vitest; integration tests against real PostgreSQL (Testcontainers); Docker packaging** | Async error handling; input validation at the trust boundary; structured logs with request IDs; transactions and constraints need real-database tests | Jest; mocked databases |
| T11 | **Error responses are `{error:{code, requestId, details}}` with no human-readable message and no parameters:** `details` is always an array of `{path, code}`, `path` is only a place in the request input (`""` for the whole body or none), every field-caused error points at its field, and a code family that differs only by resource is one code (`TAKEN`, `VERSION_CHANGED`); every detail code is listed in one registry, `DETAIL_CODES` (Phase 8, P8.4) | Clients localize from codes (Arabic and English), take limits from the docs, and mark fields generically; no server wording can leak internals; one handler fits every error | Message field in responses; `params` with limits and values; per-resource codes such as `PRIORITY_NAME_TAKEN` |
| T12 | **Toolchain:** Node 24 LTS (pinned through pnpm `devEngines`), pnpm, ESM, `tsx`, tsup, Biome, Vitest with Testcontainers, PostgreSQL 18; argon2id via `@node-rs/argon2`; JWTs via `jose`; cookies read with `cookie-parser`; `@/` import alias for `src/` (declared in `tsconfig.json` and mirrored in `vitest.config.ts`) | Owner's choices; tests need nothing started by hand | ESLint + Prettier; `tsc` or tsdown builds |
| T13 | **Platform operators are created by the `operator:create` CLI**, not through the API | No HTTP endpoint can mint an account that reaches every tenant | Bootstrap HTTP endpoint; seeded migration |
| T14 | **Layered feature modules:** routes → controller → service → repository, each written as a factory function and composed in the module's `<feature>.routes.ts`, which `app.ts` mounts. Features live in `src/modules/<feature>/`, Express middleware in `src/middleware/` (feature-specific middleware may live in its module), and infrastructure in `db`, `http`, `logging`, `config`, `audit`. Services own transactions, receive request input already parsed by the router builder from the endpoint's declaration (T60), keep only the checks that need the database or current state, and throw `AppError`; repositories take an executor (`Db \| Tx`), never open transactions, return the query result as is (checks belong to the service), and never catch errors (known database errors are translated centrally by `fromDatabaseError`). Each feature declares its endpoints in `<feature>.endpoints.ts` (one `defineApi` group per router, T60), keeps its constants in `<feature>.constants.ts`, request and query zod schemas in `<feature>.schemas.ts`, response zod schemas in `<feature>.responses.ts` (strict objects without optional keys, Phase 8), and types in `<feature>.types.ts`, named `<Name>Type` (`LoginRequestType`, `LoginResponseType`). Global type declarations live in `src/types/<library>.ts`. | Business rules and transactions get a home that is neither HTTP nor SQL, so a service can combine repository calls and `writeAuditEntry(tx, ...)` in one transaction (T8). A layer that would only pass calls through is omitted (health has no service). | Repositories opening their own transactions; classes with constructor injection |
| T15 | **Subscription state is derived, never stored:** Active through the end date, Grace for the copied grace days, Read-only after, from the database's current date in `Asia/Riyadh` (Phase 1, P1.4) | No midnight job before Phase 7; never stale, so renewal takes effect on the next request; every instance agrees on "today" | A stored state flipped by a scheduled job |
| T16 | **Tenant routes are default-deny in Read-only:** `subscriptionGuard` refuses every unsafe method; routes that need Active opt in with `requireActiveSubscription` (Phase 1, P1.6) | A new write route is protected without its author having to remember | Per-route checks |
| T17 | **The user limit is checked by `assertSeatAvailable(tx, tenantId)` under a per-tenant advisory lock**, called by every path that adds or reactivates a member; subscription changes take the same lock (Phase 1, P1.5) | Concurrent additions cannot exceed the limit; tenants never wait for each other | A database trigger; optimistic retries |
| T18 | **Money is stored as integer halalas** (SAR, excluding VAT), and the effective price applies the plan discount then the customer discount with integer arithmetic, rounded half up, computed never stored (Phase 1, P1.19, P1.20) | No floating-point error reaches an amount; stacked discounts never exceed 100%; one function gives every screen the same price | `numeric` amounts; additive discounts |
| T19 | **Email goes through an `EmailSenderType` interface with one SMTP sender (`nodemailer`);** Mailpit is the local development SMTP server (Phase 1, P1.18) | Real email locally from day one; choosing the KSA provider becomes a configuration change; tests use a fake | Provider SDK; logging emails instead of sending |
| T20 | **Lists ordered by name use `lower(name) COLLATE "und-x-icu"`** through `byName` in `src/db/order.ts` (Phase 1, P1.24) | The same order on every server whatever its locale, for Arabic and English; matches `Intl.Collator("und")` in clients | The server's default collation; `COLLATE "C"` |
| T21 | **One `org_units` table with an immutable `kind` (`department`, `section`); links between tenant rows use composite foreign keys that include `tenant_id`** (a section's parent, a member's unit); the manager role is `tenant_members.is_manager` (Phase 2, P2.1-P2.3) | One foreign key from a member to their unit; the database refuses a cross-tenant link even if a query forgets the filter; a manager can never sit outside their unit | Separate `departments` and `sections` tables; `org_units.manager_id` |
| T22 | **Foreign-key violations join the central error map, mapped only on the side that writes into a row that just disappeared** (400 `unknown_unit`); a delete that must find its row empty locks it first (`FOR UPDATE`) (Phase 2, P2.4) | Repositories keep never catching; the concurrency loser gets a meaningful error; the self-referencing key cannot be told apart by table | Telling the two sides apart by the error's table; catching in services |
| T23 | **Emailed links live in `password_tokens` with a `purpose` (`invitation`, 72 hours; `reset`, 1 hour), stored hashed, single use, retired by a newer link or a deactivation; a reset request answers 204 before looking up the account; a password change or reset signs out the user's other sessions** (Phase 2, P2.5-P2.8) | One table and one consuming `UPDATE` for both links; no account enumeration by response or timing; a stolen session does not survive a password change | Separate tables per link; signed self-contained links (cannot be single use or retired) |
| T24 | **Tenant routes declare a permission through `requireTenantPermission`**, which reads the token's `permissions`; while the token's `roleId` is null (until Phase 3) it falls back to an interim table by membership role (Phase 2, P2.9) | Routes are written once against their final permission; Phase 3 changes only where permissions come from | Role-name checks in each route |
| T25 | **Request bodies reject fields they do not accept:** every request-body schema is a zod strict object, and `validate()` reports each unknown key as `{path, code: "unknown_field"}` at its full path (`admin.phone`, `permissions.0.note`); an update that changes nothing is `no_fields`, and other custom checks name their own code (`end_before_start`, `too_many_decimals`). Query strings and token claims stay lenient. A test fails if a `*.schemas.ts` file defines a request body with plain `z.object`. (Owner decision, 2026-10-22, during Phase 3.) | A client that sends a field the API ignores (a typo, or `roleId` on `PATCH /users` after P3.12) is told which field, instead of getting a silent 200 or a 400 with code `custom`; the client can highlight the field. Query strings carry parameters the API does not control (cache-busters, `utm_*`, proxies), and JWTs carry standard claims. | Silently dropping unknown keys (zod default; hides client mistakes); rejecting unknown query parameters too |
| T26 | **The tenant permission catalog lives in code** (`PERMISSION_CATALOG`: each key and the scopes it allows); **roles and their grants live in `roles` and `role_permissions`**, linked to members by `tenant_members.role_id` with composite foreign keys; the Tenant Admin role (`is_system`) has no stored grants, and its permissions are computed as the whole catalog at the widest scopes (Phase 3, P3.1, P3.2, P3.8) | A permission ships with the route that requires it, and routes are type-checked against the catalog; grants are queryable by permission (Phase 7's R0); later phases add permissions with no data migration | Catalog in a database table; a `permissions jsonb` column on roles; a seeded admin role granted new permissions by each phase's migration |
| T27 | **The subset rule (D2, D22) is one function, `missingGrants`, checked by `assertGrantsHeld` against the actor's role read from the database in the write's transaction, including the route's own permission;** a deactivated actor holds nothing; a refusal is 403 `PERMISSION_NOT_HELD` with a `permission_not_held` detail at the body entry that asked for the permission (`permissions.3`), or no details when no input caused it (Phase 3, P3.3, P3.4; Phase 8) | Power-granting writes never trust a token that may be 30 minutes old; one function decides every check; the client can say which permission and scope are missing | Trusting the token's permissions; a lock on the actor's role (any interleaving is already equivalent to a valid order) |
| T28 | **Role edits and deletes lock the role row (`FOR UPDATE`) before reading its grants** (Phase 3, P3.5) | An edit is judged and audited against the role as the previous edit left it, so nobody strips a power added a moment earlier; delete versus assign is decided by the lock and the foreign key, as T22 | Optimistic version checks |
| T29 | **The access token's `permissions` stays a list of keys; scopes are resolved inside each query by `withinScope`**, a SQL condition built from the caller's current unit, role, and active status (Phase 3, P3.6, P3.7) | The token answers "may you call this endpoint", the database answers "which rows": a move or a role edit applies to row visibility on the next request; Phase 6 reuses the same condition for requests | Scopes in the token (stale for up to 30 minutes); resolving units in application code before each query |
| T30 | **Holidays and seasons are one model, `calendar_periods` with a `kind`; normal hours (`working_hours`) and recurring periods are versioned by effective dates and never rewritten for days that have begun; the calendar is expanded on the fly by pure functions** (`dayHours`, `addWorkingDays`, `workingDaysBetween` in `modules/calendar/shared/`) (Phase 4, P4.5, P4.8) | Recurrence, adjustments, and versioning are written once; the rules that applied on any past date are still rows, so a closure record years later is computed from them; no generation job and no horizon | Rows generated per year ahead of time (needs a job before Phase 7); editing rows in place with history only in the audit log |
| T31 | **Hijri dates come from the runtime's ICU through `Intl` (`islamic-umalqura`), verified on Node 24; one year's occurrence can be moved or skipped to follow the official announcement** (Phase 4, P4.6) | Umm al-Qura is the Saudi civil calendar; no dependency; the moon sighting can differ by a day. ICU has data for 1300-1600 AH only, outside which nothing is produced | A Hijri library; the arithmetic Islamic calendar; `Temporal` (not in Node 24) |
| T32 | **Calendar writes take a per-tenant advisory lock keyed `calendar:<tenant_id>`**, separate from the seat lock (T17) (Phase 4, P4.10) | Two concurrent edits of one recurring period cannot both end it and create a replacement; a version's `before` in the audit is what the previous write left | Row locks per period (a split touches two rows and the tenant's rank set) |
| T33 | **Working-time arithmetic:** positions are a working day plus a fraction; sums of fractions are rounded to 1e-9 before splitting into whole days; a result at a day's opening is reported at the previous working day's closing; results are rounded down to the minute; the next-working-day search stops after 3,660 days with `CalendarExhaustedError` (Phase 4, P4.3, P4.12) | `0.05 + 15 * 0.93` is `14.000000000000002` in floating point, which would otherwise report the next opening; the bound turns a defect into an error instead of an endless loop | Exact rational arithmetic |
| T34 | **A position's holders are `tenant_members.position_id`, with a composite foreign key `(tenant_id, unit_id, position_id)` → `positions (tenant_id, unit_id, id)`;** the six built-in positions are an enum, and a stage or escalation recipient points at exactly one of a position or a built-in; `resolveAssignees` and `nextLevel` (`modules/positions/shared/resolve.ts`) read current membership, managers, and active status at the moment of the call (Phase 5, P5.3) | The database refuses a holder outside the position's unit and a move that forgets to clear the position, as T21 does for managers; one column means one position per person; built-ins have no unit, holders, or name to store | A holders table; seeded rows for the built-in positions |
| T35 | **Workflows are versioned: each save that changes the stages inserts an immutable `workflow_versions` row with its `workflow_stages` rows, and requests will reference the version;** a save names its `baseVersion` and runs under a row lock (409 `VERSION_CHANGED` at `baseVersion` when stale); `current_version_id` has a composite key to a version of the same workflow, made deferrable by a custom migration because Drizzle cannot declare it (Phase 5, P5.4, P5.5) | Running requests keep the path they were accepted with, and a future graph (transitions, conditions) is stored once per version, not copied into every request; stage rows can be referenced by foreign keys; two editors cannot overwrite each other silently | Copying the stages into each request; a `jsonb` stage list; editing in place |
| T36 | **Legal configuration is retired, never deleted; names are unique among active rows (partial indexes); retiring locks the row `FOR UPDATE` and then checks its dependents, while every write that references a row locks it `FOR SHARE` and checks it is active** (Phase 5, P5.7) | History stays readable for requests; a retired name can be reused; a retire and a save that names the same row cannot both pass their checks | Hard deletes with foreign-key errors; optimistic checks |
| T37 | **Every UUID from untrusted input passes through `idSchema` (`src/http/validate.ts`), which lower-cases it** (found in Phase 5 step 5.4) | PostgreSQL accepts either case, but services compare IDs as strings (a stage's position against the rows locked for it), so an upper-case ID was reported as unknown | Lower-casing in each service; comparing case-insensitively everywhere |
| T38 | **A service's form is a `jsonb` field list on `services`, with stable field and option IDs and a `form_revision` checked on save under a row lock** (409 `VERSION_CHANGED` at `baseRevision` when stale); a field's type never changes; its structure is one zod schema (Phase 5.5, P5.5.2) | Nothing references a field, since answers carry their own copy, and the form is read and written whole; stable IDs let reports follow a field across renames | Field and option tables; editing without a revision |
| T39 | **A file's row is written before its bytes and moves `uploading` → `pending` → `attached`, or to `discarded`; the storage key is `<tenant_id>/<file_id>`, derived and never the user's name; uploads send raw bytes, one file per request, name in the query string, `Content-Length` required, and are mounted before the JSON-only body rule** (Phase 5.5, P5.5.3, P5.5.4) | The database is the one list of stored objects, so cleanup never scans the bucket and a crash leaves a row to find; no multipart parser dependency | Bytes first; multipart uploads; storing the key |
| T40 | **Object storage sits behind `FileStoreType` (`put`, `get`, `delete`), implemented with the AWS SDK v3 for any S3-compatible store; SeaweedFS serves local development and tests** (Phase 5.5, P5.5.5) | As T19 does for email: choosing the KSA provider is a configuration change, and tests run against a real S3 server | Local disk; MinIO (repository archived, images no longer published); Garage (cluster setup before first use) |
| T41 | **Uploads reserve their declared size under a per-tenant advisory lock `uploads:<tenant_id>`, in the short transaction that also checks the per-person quota and inserts the `uploading` row; usage is `sum(size_bytes)`, never a stored counter** (Phase 5.5, P5.5.6) | Two concurrent uploads cannot both pass the storage limit, as T17 does for seats; the lock is never held while bytes stream; usage cannot drift from the files that exist | Checking after the bytes arrive; a usage counter |
| T42 | **Cleanup is `sweepFiles`, run as the `files.sweep` job of the shared scheduler (T47) in each API instance: every 15 minutes after the previous run, batches of 100 rows `FOR UPDATE SKIP LOCKED`, one `DeleteObjects` call, then the rows, then commit, within a 2-minute budget** (Phase 5.5, P5.5.9) | No job runner exists before Phase 7; several instances split the work; a store failure rolls the batch back, so bytes never outlive their row | A cron container; a job queue now |
| T43 | **Numbers come from a `number_sequences` row per (tenant, prefix, year), incremented by one `insert ... on conflict do update ... returning` in the record's own transaction; the year is `now()` in Riyadh time** (Phase 6, P6.1) | The row lock serializes concurrent submissions, and a rollback also rolls back the increment, so numbers have no gaps; a new prefix is a value, not a table | A PostgreSQL sequence (gaps on rollback); `max(number) + 1` (races) |
| T44 | **A stage run is a row in `request_stage_runs` with its assignees in `request_stage_assignees`; a partial unique index allows one `active` or `held` run per request; ended runs and their assignee rows are kept as history** (Phase 6, P6.3) | "Waiting on me" is one indexed query, the database itself refuses two live runs, and the history shows who each stage waited on | Resolving assignees on every read; a state column on the request |
| T45 | **Request visibility is one SQL condition, `visibleRequests`, used by lists, reads, and every action's lookup: parties, live-run assignees, reviewers in review, and `withinScope` (T29) over the requester's and handler's recorded units** (Phase 6, P6.5) | One definition of "who sees a request", so a list and an action can never disagree; anything not visible is 404 | Checking visibility in application code after loading |
| T46 | **Every request action locks the request row `FOR UPDATE` before checking its state, and party and permission checks read the database inside that transaction** (Phase 6, P6.8) | One rule serializes accept against withdraw, two completes, and attach against close, and a deactivated member's still-valid token cannot act | Optimistic version columns; per-action locks |
| T47 | **Background work is a list of jobs (`JobType`: name, interval, `run`) run by one in-process scheduler, a `setTimeout` chain per job that starts the next run an interval after the previous one ends; the `JOBS` setting (`all`, `none`, or names) chooses which jobs a process runs; every job is safe in several processes at once and depends only on its context** (Phase 7, P7.1) | No new dependency or deployable now; a job never overlaps itself, and a slow job never delays another; moving any job to a worker of its own later is an entrypoint and a setting, not a rewrite. Jobs today: `requests.escalations` (1 minute), `subscriptions.notices` (1 hour), `files.sweep` (15 minutes), `auth.token_cleanup` and `notifications.cleanup` (daily) | `pg-boss` (a queue in PostgreSQL; worth it for retries and many job kinds); a separate worker process now; a cron container |
| T48 | **The escalation check recomputes every due moment each minute from the tenant's current calendar and settings; no due time is stored or scheduled** (Phase 7, P7.2) | The deadline of an open request follows calendar changes (D39), so a stored or scheduled moment would go stale; deadlines are whole minutes (T33) | A job scheduled per request and rule; stored due times updated on every calendar write |
| T49 | **A firing is a `request_escalations` row with primary key `(request_id, rule)`, inserted with `on conflict do nothing` in a transaction that first locks the request `FOR UPDATE SKIP LOCKED` and re-checks its state and the rule; a firing that fails rolls back whole and is retried on the next run** (Phase 7, P7.3) | "At most once" (D9) is a database fact across instances; a request closed a second earlier is never reported late (as T46); a request someone is acting on is skipped, not waited for | A flag column per rule on `requests`; an advisory lock per run |
| T50 | **Notifications are one row per recipient, written by `notify(tx, ...)` in the transaction of the event they report, holding a kind and the values the client words them from; they are read by polling, and read ones are deleted after 90 days; the `/notifications` routes skip the subscription guard, an exception to T16** (Phase 7, P7.8, P7.7) | Read state belongs to each person; no lost or orphan notification (as T8); the client localizes (T11); no push infrastructure in the MVP (D10); people can read and clear their inbox in Read-only (D44) | One event row with a recipients table; text stored in the row; WebSocket or SSE push |
| T51 | **Warnings sent once are remembered in `tenant_notices`, keyed by tenant, kind, and a key: the subscription's end date for its three warnings, so an extension re-arms them, and a fixed key for the storage warning, whose row an upload deletes when it sees usage below 80%** (Phase 7, P7.10) | Subscription state stays derived (T15); only the fact that a warning was sent is stored; no repeats while usage hovers near 90%, a new warning after a real cleanup | A stored subscription state; a warning on every crossing |
| T52 | **Every success body is `{data}`:** an object for one item or a composite view, an array for a list (with `page`), 204 with no body when nothing is left to show; 201 only for a new resource with its own URL; a write returns the resource it changed exactly as its read returns it; every key is always present, `null` when empty, including across the variants of one shape (form fields, weekdays, assignee targets, calendar periods) (Phase 8, P8.2) | One unwrapping for every call, no refetch after a write, and no optional keys in the client's types | Bare objects and arrays; named keys (`{priority}`); writes returning only what changed |
| T53 | **Every list is paged by an opaque cursor through `listPage`:** the cursor carries the last row's sort values as exact database text (microseconds kept) and the first 16 hex characters of a SHA-256 fingerprint of the list and its validated filters; one server-side order per list with the ID as tie-breaker, all keys in one direction; `total` from a count over the same filters in the page's `READ ONLY REPEATABLE READ` snapshot; `limit` 1-100, default 25; a code-held list (the permission catalog) is paged in memory with the same rules (Phase 8, P8.3) | No repeats or skips on live data; a cursor reused with other filters fails as `invalid_cursor` instead of returning a wrong page; the page and its total always agree | Offsets (shift on inserts); a cursor of the last ID (breaks when that row is deleted); client-chosen sorting; a signed cursor (visibility is decided in SQL anyway) |
| T54 | **One filter rule for every list:** `field=value` keeps matching items, every filter accepts `all`, a filter left out takes the list's documented default, `none` asks for an empty field; `q` and `view` are documented per list; list query schemas are built from `booleanFilter`, `valueFilter`, `idFilter`, and `pageQuery` (Phase 8, P8.5) | One filter control works on every list; the defaults live in the schemas, so the docs, the query, and the cursor fingerprint agree | Per-list conventions (`includeRetired`, `unread=false` as no filter) |
| T55 | **Responses are written only through `sendData`, `sendPage`, and `sendNoContent`, which check the value against its response schema outside production** (one process-wide setting from `buildApp`); downloads keep `sendDownload` (Phase 8, P8.7) | The whole test suite checks every response it receives, so a field added without its schema, or one that leaks (a hash), fails a test; in production a mismatch never breaks a working call | A separate contract test per endpoint; checking in production too |
| T56 | **Contract tests tie code to docs in both directions:** no controller writes a response directly (C1); response schemas are strict objects without `.optional()`, `.nullish()`, or `.partial()`; every error and detail code is in `docs/api/errors.md` and every code there exists (C4); every mounted route is a row of a `.API.md` table of a phase in implementation or implemented, and every such row is a route (C5) (Phase 8, P8.7; amended in Phase 10, Q15) | "No exceptions" survives new endpoints: a deviation fails a test before review instead of reaching the frontend | Review only (OpenAPI generated from code was rejected here and adopted in Phase 10, T60) |
| T57 | **One configuration loader in `src/config/`, read once at startup:** a zod schema over the environment variables (names unchanged) returns a grouped `Config` (`server`, `frontend`, `database`, `auth`, `smtp`, `storage`, `scheduler`, `jobs`, renamed by the owner on 2026-10-28); each router, job, and infrastructure factory receives only its groups, typed `<Group>ConfigType`; the CLIs validate through `parseCliConfig`, which shares the `DATABASE_URL` field and needs nothing else; `process.env` is read only as the argument of a `src/config/` function in `main.ts` and `src/cli/`; `.env.example` lists every key, optional ones set to or commented with their default, and contract tests enforce both rules; a change takes effect on restart (Phase 9, P9.1, P9.5, P9.7) | One place to see what a deployment can change and one signature to see what a module depends on; a module cannot reach a secret it does not use; existing `.env` files keep working | Flat config passed to every module; `node-config` or `convict` (layered files, weaker typing); live reload |
| T58 | **Operational settings are central, bounded, and overridable:** job intervals, batch sizes, and budgets (`JOB_<JOB NAME>_<SETTING>`), `DATABASE_TIMEOUT_MS`, `SHUTDOWN_TIMEOUT_MS`, and `STORAGE_UPLOAD_QUEUE_SIZE`, defaulting to the values the code used before; budgets are bounded like intervals but not compared with them, and an unknown `JOB_*` key is ignored (both checks removed on 2026-10-28); the startup log lists each job's effective settings, never secrets (Phase 9, P9.2, P9.4, P9.8) | Staging and production tune a job with a restart, not a code change; each default lives only in the schema | Fixed constants in each module; fatal unknown keys (breaks hosts such as Jenkins that set `JOB_NAME`) |

| T60 | **Every endpoint is declared once as data and everything else is built from it:** `<module>.endpoints.ts` holds `defineEndpoint` entries (method, path, summary, realm, permission, active subscription, params, query, body, response kind/status/schema, errors) in `defineApi` groups; `buildRouter` mounts realm guards, permission, then validates params (a failure is 404 `NOT_FOUND`), query, and body (400 `VALIDATION_FAILED`), calls the handler with the parsed input, and sends the value it returns with the declared kind; no routes file mounts a route by hand (Phase 10, P10.2, P10.7) | The schema that is enforced is the schema that is documented, and a handler cannot answer with another status or shape than the document shows | Validation in services with declarations naming the schemas; controllers calling `sendData` themselves |
| T61 | **`docs/api/openapi.json` is an OpenAPI 3.1 document generated from the declarations with Zod's own `z.toJSONSchema`** (no library), committed, and checked by a drift test and `@scalar/openapi-parser`; errors per operation are the declared codes plus those implied by realm, permission, and inputs; components are named by `.meta({ id })`; no examples. ### Deferred Hardening

Each item below is a known, accepted gap for the MVP stage, with the trigger that should bring it back.

| Item | What the MVP does instead | Add it when |
| ---- | ------------------------- | ----------- |
| Row-Level Security for tenant isolation | Application-level `tenant_id` filters (T2), covered by isolation tests | Before the first production tenant with sensitive data, or when the number of tenant-data queries makes review unreliable |
| Database-enforced append-only audit (no `UPDATE`/`DELETE` grants) | No code path updates or deletes audit rows | Together with dedicated database roles |
| Login throttling (per account and per IP) | None | Before production exposure |
| Rate limiting of password-reset requests (per email and per IP) | Every request gets the same 204; only real, active, verified users are emailed, and only the newest link works | Before production exposure, together with login throttling |
| Refresh-token reuse detection (revoke all of a user's tokens when a revoked token is replayed) | A revoked token is simply rejected | Before production exposure |
| CSRF tokens | `SameSite=Lax` cookies, a web app on the same site as the API, and CORS limited to that app's origin (T63) | If the API is served from a different site than the web app, or before production exposure |
| Separate operator identity realm | `users.role = 'operator'` (T4) | When operator roles or stricter operator policies are needed |
| MFA and enterprise SSO | Email and password only | After the MVP |
| Virus scanning of uploaded files | An allow-list of types detected from the content (no legacy Office formats), and files served only as sandboxed downloads (Phase 5.5 spec, Q6) | Before production |
| Separate worker process for background jobs | Every API instance runs the jobs `JOBS` selects, all by default (T47) | When jobs slow the API's responses, or when the API scales to more instances than the jobs need |
| Stored due times for the escalation check | Every open request is recomputed each minute (T48) | When a run of `requests.escalations` takes a noticeable share of its minute |
| Live push of notifications to the browser (SSE or WebSocket) | The client polls the unread count (T50) | When users need alerts faster than the polling interval, or polling load matters |
| Monitoring that alerts when a job keeps failing | Failures are logged at error with the job and run ID; the file sweep also warns when files are overdue | Before production |
| Opt-in list totals (`?withTotal=true`) | Every list page counts its matches in the page's snapshot (T53) | When counting a list takes a noticeable share of its response time |
| Secrets read from files (`JWT_SECRET_FILE=/run/secrets/jwt`) or a secret manager | Plain environment variables, validated and never logged (T57) | The staging phase, where the host first delivers secrets as files; before production |

### Deferred Technical Decisions

- **Client-chosen list sorting** (`sort=` by column): each list has one server-side order (T53); add sort options, each with its own index and cursor keys, when a screen needs another order of a long list (Phase 8, Q7).
- **Hosting provider in KSA:** decided at deployment; Docker keeps options open. The managed PostgreSQL must offer version 18, built with ICU (the `und-x-icu` collation orders names; Phase 1 spec, P1.24).
- **Email provider for verification emails** (MVP D16): must keep data in KSA and accept SMTP; until then Mailpit serves local development (Phase 1 spec, P1.18). Must be chosen before production.
