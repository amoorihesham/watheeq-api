# Technical Decisions

## Watheeq - Legal Affairs Management System

**Status:** Revised 2026-10-21 to match the simplified MVP codebase; Phase 3 and Phase 4 decisions added 2026-10-22; Phase 5 decisions added 2026-10-24.
The full design for T1-T13 is in `docs/specs/phase-0-foundations.md`, T14 in `docs/specs/phase-0.5-refactor.md`, T15-T20 in `docs/specs/phase-1-platform-subscriptions.md`, T21-T24 in `docs/specs/phase-2-org-structure-users.md`, T25 in this log only (a cross-cutting change made during Phase 3), T26-T29 in `docs/specs/phase-3-roles-authorization.md`, T30-T33 in `docs/specs/phase-4-working-calendar.md`, and T34-T37 in `docs/specs/phase-5-legal-configuration.md`.
**Scope of this doc:** Technology and architecture decisions. Product and scope decisions live in `MVP_SCOPE.md` (D1-D33).

**Guiding rule:** for the MVP, choose the simplest design that is correct for the current requirements.
Hardening that the MVP does not need yet is listed under "Deferred hardening" and added when the product grows.

---

### Constraints

- **Language / framework:** Node.js + TypeScript, Express.
- **Data residency:** all tenant data must remain in Saudi Arabia.
  This includes databases, backups, logs, and any third-party service that receives tenant data (for example error tracking or an email provider).
- **Primary client:** a browser web app. A mobile app is a distant future client.

### Decision Log

| #   | Decision | Rationale | Alternatives considered |
| --- | -------- | --------- | ----------------------- |
| T1  | **PostgreSQL** as the database | Relational data (org tree, roles, requests), strong transactions, managed offerings available in KSA | MySQL, MongoDB (poor fit for relational data and cross-document transactions) |
| T2  | **Tenant isolation: shared tables with a `tenant_id` column, filtered in application code.** Every repository function that reads or writes tenant data takes the tenant ID and filters by it. One database role is used for everything. | Simplest model to build, run, and debug; no database roles or policies to provision on the KSA host. The data layout is the same one RLS needs, so RLS can be added later without moving data. | PostgreSQL Row-Level Security (stronger: the database refuses cross-tenant rows even if a query forgets the filter; deferred), schema or database per tenant |
| T3  | **Drizzle ORM** for data access; **migrations generated by Drizzle Kit** from `src/db/schema/` | Typed queries and explicit transactions; one source of truth for tables, no hand-written SQL migrations | Kysely, Prisma |
| T4  | **One `users` table for every account**, with a `role` column: `operator` (platform operator, belongs to no tenant) or `user` (tenant user) | One login flow, one table, one set of auth code | Separate `operators` table and login realm (stronger separation; deferred) |
| T5  | **Tenant membership through a `tenant_members` table** with a unique `user_id`, so a user belongs to exactly one tenant, and a `role` for the user inside the tenant (`admin` or `member` until Phase 3 replaces it with tenant-defined roles). `tenants.owner_id` points to the tenant's owner. | Keeps `users` free of tenant columns (operators have none), while the unique constraint keeps the MVP's one-user-one-tenant rule a database fact | `users.tenant_id` column; many-to-many membership (not needed by the MVP) |
| T6  | **Email is unique across the platform**; login finds the user, and through membership the tenant, from the email | Matches one-user-one-tenant; no tenant code or subdomain at login | Subdomain per tenant, tenant code at login |
| T7  | **Authentication with tokens in httpOnly cookies:** a signed JWT access token (30 minutes; payload `{sub, iss: "watheeq_api", iat, exp, username, email, role, tenant}`) and an opaque refresh token (7 days) stored hashed in the database, rotated on every refresh, revoked on logout; refresh rejects inactive users | No database read on ordinary requests; a deactivated user loses access within 30 minutes; one mechanism for operators and tenant users | Server-side sessions in PostgreSQL (immediate revocation, but a database read per request), external IdP (extra infrastructure, residency concerns) |
| T8  | **Audit entries are written in the same transaction** as the business change, through `writeAuditEntry(tx, entry)`, which accepts only a transaction | Audit can never disagree with the actual data | Log files, asynchronous audit writes |
| T9  | **Modular monolith** organized by feature modules | One deployable; clear module boundaries without network and operational overhead | Microservices |
| T10 | **Express 5, zod, pino, Vitest; integration tests against real PostgreSQL (Testcontainers); Docker packaging** | Async error handling; input validation at the trust boundary; structured logs with request IDs; transactions and constraints need real-database tests | Jest; mocked databases |
| T11 | **Error responses are `{error:{code, requestId, details?}}` with no human-readable message** | Clients localize from codes (Arabic and English); no server wording can leak internals | Message field in responses |
| T12 | **Toolchain:** Node 24 LTS (pinned through pnpm `devEngines`), pnpm, ESM, `tsx`, tsup, Biome, Vitest with Testcontainers, PostgreSQL 18; argon2id via `@node-rs/argon2`; JWTs via `jose`; cookies read with `cookie-parser`; `@/` import alias for `src/` (declared in `tsconfig.json` and mirrored in `vitest.config.ts`) | Owner's choices; tests need nothing started by hand | ESLint + Prettier; `tsc` or tsdown builds |
| T13 | **Platform operators are created by the `operator:create` CLI**, not through the API | No HTTP endpoint can mint an account that reaches every tenant | Bootstrap HTTP endpoint; seeded migration |
| T14 | **Layered feature modules:** routes → controller → service → repository, each written as a factory function and composed in the module's `<feature>.routes.ts`, which `app.ts` mounts. Features live in `src/modules/<feature>/`, Express middleware in `src/middleware/` (feature-specific middleware may live in its module), and infrastructure in `db`, `http`, `logging`, `config`, `audit`. Services own transactions, validate with zod, and throw `AppError`; repositories take an executor (`Db \| Tx`), never open transactions, return the query result as is (checks belong to the service), and never catch errors (known database errors are translated centrally by `fromDatabaseError`). Each feature keeps its constants in `<feature>.config.ts`, zod schemas in `<feature>.schemas.ts`, and types in `<feature>.types.ts`, named `<Name>Type` (`LoginRequestType`, `LoginResponseType`). Global type declarations live in `src/types/<library>.ts`. | Business rules and transactions get a home that is neither HTTP nor SQL, so a service can combine repository calls and `writeAuditEntry(tx, ...)` in one transaction (T8). A layer that would only pass calls through is omitted (health has no service). | Repositories opening their own transactions; classes with constructor injection |
| T15 | **Subscription state is derived, never stored:** Active through the end date, Grace for the copied grace days, Read-only after, from the database's current date in `Asia/Riyadh` (Phase 1, P1.4) | No midnight job before Phase 7; never stale, so renewal takes effect on the next request; every instance agrees on "today" | A stored state flipped by a scheduled job |
| T16 | **Tenant routes are default-deny in Read-only:** `subscriptionGuard` refuses every unsafe method; routes that need Active opt in with `requireActiveSubscription` (Phase 1, P1.6) | A new write route is protected without its author having to remember | Per-route checks |
| T17 | **The user limit is checked by `assertSeatAvailable(tx, tenantId)` under a per-tenant advisory lock**, called by every path that adds or reactivates a member; subscription changes take the same lock (Phase 1, P1.5) | Concurrent additions cannot exceed the limit; tenants never wait for each other | A database trigger; optimistic retries |
| T18 | **Money is stored as integer halalas** (SAR, excluding VAT), and the effective price applies the plan discount then the customer discount with integer arithmetic, rounded half up, computed never stored (Phase 1, P1.19, P1.20) | No floating-point error reaches an amount; stacked discounts never exceed 100%; one function gives every screen the same price | `numeric` amounts; additive discounts |
| T19 | **Email goes through an `EmailSenderType` interface with one SMTP sender (`nodemailer`);** Mailpit is the local development SMTP server (Phase 1, P1.18) | Real email locally from day one; choosing the KSA provider becomes a configuration change; tests use a fake | Provider SDK; logging emails instead of sending |
| T20 | **Lists ordered by name use `lower(name) COLLATE "und-x-icu"`** through `byName` in `src/db/order.ts` (Phase 1, P1.24) | The same order on every server whatever its locale, for Arabic and English; matches `Intl.Collator("und")` in clients | The server's default collation; `COLLATE "C"` |
| T21 | **One `org_units` table with an immutable `kind` (`department`, `section`); links between tenant rows use composite foreign keys that include `tenant_id`** (a section's parent, a member's unit); the manager role is `tenant_members.is_manager` (Phase 2, P2.1-P2.3) | One foreign key from a member to their unit; the database refuses a cross-tenant link even if a query forgets the filter; a manager can never sit outside their unit | Separate `departments` and `sections` tables; `org_units.manager_id` |
| T22 | **Foreign-key violations join the central error map, mapped only on the side that writes into a row that just disappeared** (400 `unknown_unit`); a delete that must find its row empty locks it first (`FOR UPDATE`) (Phase 2, P2.4) | Repositories keep never catching; the concurrency loser gets a meaningful error; the self-referencing key cannot be told apart by table | Telling the two sides apart by the error's table; catching in services |
| T23 | **Emailed links live in `password_tokens` with a `purpose` (`invitation`, 72 hours; `reset`, 1 hour), stored hashed, single use, retired by a newer link or a deactivation; a reset request answers 204 before looking up the account; a password change or reset signs out the user's other sessions** (Phase 2, P2.5-P2.8) | One table and one consuming `UPDATE` for both links; no account enumeration by response or timing; a stolen session does not survive a password change | Separate tables per link; signed self-contained links (cannot be single use or retired) |
| T24 | **Tenant routes declare a permission through `requireTenantPermission`**, which reads the token's `permissions`; while the token's `roleId` is null (until Phase 3) it falls back to an interim table by membership role (Phase 2, P2.9) | Routes are written once against their final permission; Phase 3 changes only where permissions come from | Role-name checks in each route |
| T25 | **Request bodies reject fields they do not accept:** every request-body schema is a zod strict object, and `validate()` reports each unknown key as `{path, code: "unknown_field"}` at its full path (`admin.phone`, `permissions.0.note`); an update that changes nothing is `no_fields`, and other custom checks name their own code (`end_before_start`, `too_many_decimals`). Query strings and token claims stay lenient. A test fails if a `*.schemas.ts` file defines a request body with plain `z.object`. (Owner decision, 2026-10-22, during Phase 3.) | A client that sends a field the API ignores (a typo, or `roleId` on `PATCH /users` after P3.12) is told which field, instead of getting a silent 200 or a 400 with code `custom`; the client can highlight the field. Query strings carry parameters the API does not control (cache-busters, `utm_*`, proxies), and JWTs carry standard claims. | Silently dropping unknown keys (zod default; hides client mistakes); rejecting unknown query parameters too |
| T26 | **The tenant permission catalog lives in code** (`PERMISSION_CATALOG`: each key and the scopes it allows); **roles and their grants live in `roles` and `role_permissions`**, linked to members by `tenant_members.role_id` with composite foreign keys; the Tenant Admin role (`is_system`) has no stored grants, and its permissions are computed as the whole catalog at the widest scopes (Phase 3, P3.1, P3.2, P3.8) | A permission ships with the route that requires it, and routes are type-checked against the catalog; grants are queryable by permission (Phase 7's R0); later phases add permissions with no data migration | Catalog in a database table; a `permissions jsonb` column on roles; a seeded admin role granted new permissions by each phase's migration |
| T27 | **The subset rule (D2, D22) is one function, `missingGrants`, checked by `assertGrantsHeld` against the actor's role read from the database in the write's transaction, including the route's own permission;** a deactivated actor holds nothing; a refusal is 403 `PERMISSION_NOT_HELD` with details `{path: <permission>, code: "permission_not_held", scope}` (Phase 3, P3.3, P3.4) | Power-granting writes never trust a token that may be 30 minutes old; one function decides every check; the client can say which permission and scope are missing | Trusting the token's permissions; a lock on the actor's role (any interleaving is already equivalent to a valid order) |
| T28 | **Role edits and deletes lock the role row (`FOR UPDATE`) before reading its grants** (Phase 3, P3.5) | An edit is judged and audited against the role as the previous edit left it, so nobody strips a power added a moment earlier; delete versus assign is decided by the lock and the foreign key, as T22 | Optimistic version checks |
| T29 | **The access token's `permissions` stays a list of keys; scopes are resolved inside each query by `withinScope`**, a SQL condition built from the caller's current unit, role, and active status (Phase 3, P3.6, P3.7) | The token answers "may you call this endpoint", the database answers "which rows": a move or a role edit applies to row visibility on the next request; Phase 6 reuses the same condition for requests | Scopes in the token (stale for up to 30 minutes); resolving units in application code before each query |
| T30 | **Holidays and seasons are one model, `calendar_periods` with a `kind`; normal hours (`working_hours`) and recurring periods are versioned by effective dates and never rewritten for days that have begun; the calendar is expanded on the fly by pure functions** (`dayHours`, `addWorkingDays`, `workingDaysBetween` in `modules/calendar/shared/`) (Phase 4, P4.5, P4.8) | Recurrence, adjustments, and versioning are written once; the rules that applied on any past date are still rows, so a closure record years later is computed from them; no generation job and no horizon | Rows generated per year ahead of time (needs a job before Phase 7); editing rows in place with history only in the audit log |
| T31 | **Hijri dates come from the runtime's ICU through `Intl` (`islamic-umalqura`), verified on Node 24; one year's occurrence can be moved or skipped to follow the official announcement** (Phase 4, P4.6) | Umm al-Qura is the Saudi civil calendar; no dependency; the moon sighting can differ by a day. ICU has data for 1300-1600 AH only, outside which nothing is produced | A Hijri library; the arithmetic Islamic calendar; `Temporal` (not in Node 24) |
| T32 | **Calendar writes take a per-tenant advisory lock keyed `calendar:<tenant_id>`**, separate from the seat lock (T17) (Phase 4, P4.10) | Two concurrent edits of one recurring period cannot both end it and create a replacement; a version's `before` in the audit is what the previous write left | Row locks per period (a split touches two rows and the tenant's rank set) |
| T33 | **Working-time arithmetic:** positions are a working day plus a fraction; sums of fractions are rounded to 1e-9 before splitting into whole days; a result at a day's opening is reported at the previous working day's closing; results are rounded down to the minute; the next-working-day search stops after 3,660 days with `CalendarExhaustedError` (Phase 4, P4.3, P4.12) | `0.05 + 15 * 0.93` is `14.000000000000002` in floating point, which would otherwise report the next opening; the bound turns a defect into an error instead of an endless loop | Exact rational arithmetic |
| T34 | **A position's holders are `tenant_members.position_id`, with a composite foreign key `(tenant_id, unit_id, position_id)` → `positions (tenant_id, unit_id, id)`;** the six built-in positions are an enum, and a stage or escalation recipient points at exactly one of a position or a built-in; `resolveAssignees` and `nextLevel` (`modules/positions/shared/resolve.ts`) read current membership, managers, and active status at the moment of the call (Phase 5, P5.3) | The database refuses a holder outside the position's unit and a move that forgets to clear the position, as T21 does for managers; one column means one position per person; built-ins have no unit, holders, or name to store | A holders table; seeded rows for the built-in positions |
| T35 | **Workflows are versioned: each save that changes the stages inserts an immutable `workflow_versions` row with its `workflow_stages` rows, and requests will reference the version;** a save names its `baseVersion` and runs under a row lock (409 `WORKFLOW_VERSION_CHANGED` when stale); `current_version_id` has a composite key to a version of the same workflow, made deferrable by a custom migration because Drizzle cannot declare it (Phase 5, P5.4, P5.5) | Running requests keep the path they were accepted with, and a future graph (transitions, conditions) is stored once per version, not copied into every request; stage rows can be referenced by foreign keys; two editors cannot overwrite each other silently | Copying the stages into each request; a `jsonb` stage list; editing in place |
| T36 | **Legal configuration is retired, never deleted; names are unique among active rows (partial indexes); retiring locks the row `FOR UPDATE` and then checks its dependents, while every write that references a row locks it `FOR SHARE` and checks it is active** (Phase 5, P5.7) | History stays readable for requests; a retired name can be reused; a retire and a save that names the same row cannot both pass their checks | Hard deletes with foreign-key errors; optimistic checks |
| T37 | **Every UUID from untrusted input passes through `idSchema` (`src/http/validate.ts`), which lower-cases it** (found in Phase 5 step 5.4) | PostgreSQL accepts either case, but services compare IDs as strings (a stage's position against the rows locked for it), so an upper-case ID was reported as unknown | Lower-casing in each service; comparing case-insensitively everywhere |

### Deferred Hardening

Each item below is a known, accepted gap for the MVP stage, with the trigger that should bring it back.

| Item | What the MVP does instead | Add it when |
| ---- | ------------------------- | ----------- |
| Row-Level Security for tenant isolation | Application-level `tenant_id` filters (T2), covered by isolation tests | Before the first production tenant with sensitive data, or when the number of tenant-data queries makes review unreliable |
| Database-enforced append-only audit (no `UPDATE`/`DELETE` grants) | No code path updates or deletes audit rows | Together with dedicated database roles |
| Login throttling (per account and per IP) | None | Before production exposure |
| Rate limiting of password-reset requests (per email and per IP) | Every request gets the same 204; only real, active, verified users are emailed, and only the newest link works | Before production exposure, together with login throttling |
| Refresh-token reuse detection (revoke all of a user's tokens when a revoked token is replayed) | A revoked token is simply rejected | Before production exposure |
| CSRF tokens | `SameSite=Lax` cookies and a same-origin deployment | If the API is served from a different site than the web app, or before production exposure |
| Separate operator identity realm | `users.role = 'operator'` (T4) | When operator roles or stricter operator policies are needed |
| MFA and enterprise SSO | Email and password only | After the MVP |

### Deferred Technical Decisions

- **Background job runner:** decided in Phase 7 (escalation checks).
- **Hosting provider in KSA:** decided at deployment; Docker keeps options open. The managed PostgreSQL must offer version 18, built with ICU (the `und-x-icu` collation orders names; Phase 1 spec, P1.24).
- **Email provider for verification emails** (MVP D16): must keep data in KSA and accept SMTP; until then Mailpit serves local development (Phase 1 spec, P1.18). Must be chosen before production.
